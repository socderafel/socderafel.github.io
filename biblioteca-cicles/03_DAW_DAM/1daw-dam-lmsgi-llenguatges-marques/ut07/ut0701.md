En el desenvolupament de programari i l'administració de sistemes moderns, la informació rara vegada permanece estàtica en un únic lloc. Les dades fluyen constantement entre servidors, bases de dades, aplicacions mòbils i navegadors web. No obstant això, no tots aquests sistemes "parlen" el mateix idioma estructural. Ací és on entra en joc la **conversió de documents**.

## **El problema de l'heterogeneitat de sistemes**

La **heterogeneitat** es refereix a la diversitat de tecnologies, llenguatges de programació, sistemes operatius i arquitectures que conviven en l'ecosistema informàtic actual.

És extremadament raro que una empresa utilitze una única tecnologia per a tot. L'habitual és trobar:
- Sistemes *Legacy* (heretats), com un antic servidor bancario escrit en Java o COBOL que exporta dades estrictament en **XML**.
- Aplicacions modernes, com un *frontend* desenvolupat en React o Vue.js que espera consumir dades ligeros en **JSON**.
- Bases de dades relacionals (SQL) convivent amb bases de dades documentals (NoSQL com MongoDB).

**Exemple del problema:**
Imagina que el sistema d'inventari d'una botiga de ropa és antic i genera un catàleg diario en format XML. No obstant això, la nova App mòbil de la botiga està programada en React Native i requereix que les dades del catàleg arriben en format JSON perquè la carrega siga ràpida. Si enviem el XML directament a la App mòbil, aquesta no sabrá com interpretar-lo nativament de forma eficient o el procés serà molt costoso en recursos per al telèfon. Existeix una barrera de comunicació.

## **Avantatges i casos d'ús comuns de la transformació de dades**

La conversió o transformació de dades actua com un "traductor universal" en mitjà d'aquesta heterogeneitat. Consisteix en prendre un document d'origen, procesar-lo aplicant una sèrie de regles, i generar un document de destí amb un format o estructura diferent.

**Avantatges principals:**
1. **Desacoplament:** Els sistemes no necessiten conèixer com funciona l'un altre internament; només acuerdan un format d'intercanvi.
2. **Seguretat i filtrat:** Permet eliminar dades sensibles. Podem transformar un document complet i generar un nou que omita contrasenyes o dades personals abans d'enviar-lo al client.
3. **Optimització:** Reducció del mida (pes) de les dades a l'eliminar etiquetes innecesarias o canviar a formats més ligeros.

**Casos d'ús comuns:**
- **Microservicios:** Xicotetes aplicacions independents que es comuniquen entre sí. Un microservicio de pagaments pot requerir dades en un format específic distint al microservicio d'envíos.
- **Migracions:** Al canviar d'un programari a un altre (per exemple, canviar d'un ERP antic a SAP), és necessari exportar tota la base de dades antiga i transformar-la perquè el nou sistema puga importar-la.

## **Àmbits d'aplicació**

La conversió de documents és una tasca diaria en múltiples escenarios del sector IT:

### A. Integració B2B (Business-to-Business)

Quan dos empreses diferents necessiten intercanviar dades automàticament.
* **Exemple:** Un proveïdor de peces de cotxe (Empresa A) envia diariament el seu catàleg de productes. El seu sistema l'exporta en XML. El taller mecánic (Empresa B) té un programari de gestió modern que només admet importacions en format JSON o CSV. Es requereix un procés intermedi (un *script* o una eina d'integració) que convertisca automàticament el XML del proveïdor al JSON que entén el taller.

### B. Consumo de APIs REST

Les APIs són les portes d'accés a les dades de serveis de tercers (com Google Maps, serveis del clima, pasarelas de pagament).
* **Exemple:** Una aplicació fa una petició a la API de la AEMET per a obtindre el clima. La API retorna un document JSON complex i enorme. L'aplicació transforma eixe JSON inmenso, extrayendo únicament la temperatura actual i la probabilitat de lluvia, creant un document JSON molt més xicotet que s'enviará al *smartwatch* de l'usuari.

### C. Presentació web de dades

A menudo, la informació s'emmagatzema com "dades puros" sense cap tipus d'estil visual.
* **Exemple clàssic (XSLT a HTML):** Tenim un arxiu `factura.xml` que només conté dades (números, conceptes, totals). Utilitzant una tecnologia anomenada XSLT (que aprendrem en aquesta unitat), transformamos eixes dades puros en un arxiu `factura.html` que conté taules, negritas, colors i el logotipo de l'empresa, listo per a ser visualitzat en un navegador web i impreso pel client.

### D. Publicació multicanal

El principi de "escriure una vegada, publicar en totes parts".
* **Exemple:** Un periódic digital redacta els seus articles en un format XML neutro. A partir d'eixe únic arxiu d'origen, realitzen conversions simultáneas:
    - Una transformació genera el HTML per a la pàgina web.
    - Una altra transformació genera el JSON per a la App mòbil.
    - Una altra transformació extrae només el títol i el resum per a enviar-lo automàticament a xarxes socials.

## **Evolució dels formats d'intercanvi**

Históricament, la forma en la que els sistemes intercambian informació ha evolucionado cercant sempre major eficiència i facilitat d'ús per als desenvolupadors.

### L'era de la prevalencia de XML

A principis dels 2000, **XML (eXtensible Markup Language)** era el rey absoluto indiscutible. Protocols com SOAP dependían exclusivament d'ell.
* **Pros:** Altament estructurat, estricte, permet validació exhaustiva mitjançant esquemes (XSD), ideal per a sistemes empresarials complexos i institucionals.
* **Contras:** Molt verboso (repeteix les etiquetes d'obertura i tancament constantement), el que genera arxius molt pesants. Difícil de llegir nativament en llenguatges com JavaScript.

### El predominio actual de JSON

Amb l'auge de la Web 2.0, les aplicacions de pàgina única (SPA) i el desenvolupament en JavaScript, nació **JSON (JavaScript Object Notation)**. Hui en dia és l'estàndard de facto per a la majoria de les APIs web (REST).
* **Pros:** Molt lleuger, elimina la redundància de les etiquetes, és extremadament fàcil de llegir per a humans i el seu sintaxi és codi JavaScript natiu (el que fa que els navegadors el procesen de forma quasi instantánea).
* **Contras:** Menys eines de validació estricta nativa en comparació amb XML, no suporta atributs de forma natural com XML.

### 💡 Exemple comparativo: El mateix dada en XML i JSON

Imagina que volem transmetre la informació d'un empleat. Observa la diferència de sintaxi i verbositat:

**En format XML:**

```html
<empleados>
    <empleado id="104">
        <nombre>Laura</nombre>
        <apellidos>García Pérez</apellidos>
        <departamento>Informática</departamento>
        <habilidades>
            <habilidad>Python</habilidad>
            <habilidad>React</habilidad>
        </habilidades>
    </empleado>
</empleados>
```

**En format JSON equivalent:**

```html
{
  "empleados": [
    {
      "id": 104,
      "nombre": "Laura",
      "apellidos": "García Pérez",
      "departamento": "Informática",
      "habilidades": ["Python", "React"]
    }
  ]
}
```

Com es pot observar, JSON prescinde de les etiquetes de tancament (`</nombre>`), utilitzant en el seu lloc una estructura basada en claus `{}` per a objectes i claudàtors `[]` per a llistes (arrays). Açò explica per què en l'actualitat, quan el mida del missatge i la velocitat de processament en la web són crítics, la conversió **de sistemes antics (XML) a sistemes moderns (JSON)** és una de les tasques més demandades.
