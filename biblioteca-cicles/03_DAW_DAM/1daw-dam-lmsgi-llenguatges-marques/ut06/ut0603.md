Quan parlem de la sintaxi d'una descripció de documents, ens referim a **la forma concreta en la que es escriuen les regles** que determinan si un document és vàlid o no. Cada tecnologia utilitza una sintaxi distinta, però totes comparteixen una idea comú:
**expressar regles de forma declarativa**, no mitjançant codi.

Comprendre la sintaxi no significa memoritzar paraules clau, sinó **aprendre a llegir i escriure gramátiques**, interpretant què estructura i què restriccions està imponent cada línia.

En aquest apartat es responden dos preguntes fonamentals:

- Com es escriu una gramàtica o descripció d'un document?

- Què elements i regles formen part de cada tecnologia de validació?

Comprendre l'estructura i la sintaxi d'aquestes descripcions és clau per a poder:

- dissenyar contratos de dades coherentes,

- interpretar esquemes existents,

- detectar errors de validació,

- seleccionar la tecnologia adequada en cada context.

Cada tecnologia (DTD, XSD, JSON Schema) utilitza una sintaxi diferent, però totes persiguen el mateix objectiu:
* definir formalment com ha de ser un document vàlid.

## **DTD**

Per a definir un element s'usa la sintaxi:

```html
<!ELEMENT nombre_elemento contenido>
```

L'expressió del contingut pot ser:

**ANY**

Representa qualsevol contingut. Per tant, deixa libertad absoluta, la qual cosa significa en realitat no definir res. En conseqüència, en la versió definitiva d'un DTD no hauria d'aparèixer mai, però pot ser útil en versions preliminares en les que encara no hem definit tota la gramàtica:

```html
<!ELEMENT profesor ANY>
```

**EMPTY**

Representa un element buit, açò és, un element sense contingut (encara que pot tindre atributs):

```html
<!ELEMENT hr EMPTY>
```

**(#PCDATA)**

El node conté text:

```html
<!ELEMENT apodo (#PCDATA)>
```

**(elemento_hijo)**

El node conté dins de sí un node fill:

```html
<!ELEMENT claustro (profesor)>
```

Ara bé, pel general els elements no contenen únicament un únic fill, sinó diversos el que porta a definir dos conceptes:

### **Seqüència**

que representa com es succeeixen els nodes fills dins del pare. DTD defineix dos seqüències:

Un element seguit a continuació per un altre, mitjançant la coma:

```html
<!ELEMENT profesor (apodo, nombre, apellidos, departamento)>
```

O un element i un altre element, mitjançant la tubería:

```html
<!ELEMENT claustro (profesor|lector)>
```

En aquest cas, estem afirmant que un claustro està compost per o un professor o per un lector, però no per tots dos. Sí, és alguna cosa estúpido, però encara no sabem cardinalitat.

Per supòsit, podem fer composicions de tots dos tipus de seqüències e, fins i tot, usar parèntesis per a agrupar-les. Suponent dos nodes fills anomenats a i b:

```html
(a,b)
(a|b)
(a,(b|c))
((a,b)|c)
(a,(b|c),d)
(a,((b,c)|d))
```

### **Cardinalitat**

que representa la possible repetició d'un element i que DTD la significa afegint després de l'element un modificador. El modificador permet expressar:

- **Una i només una aparició**, si no es afegeix modificador, que és el que hem fet en les expressions del contingut incloses en l'explicació sobre la seqüència.

- **Una o cap aparició**, que es expressa amb una interrogació. Per exemple:

```html
<!ELEMENT profesor (apodo?, nombre, apellidos, departamento?)>
```

En aquesta definició, cada professor obligatòriament tindrà un nom i uns cognoms, però podrà no tindre apodo o no pertànyer a un departament. Per tant, aquest node és vàlid:

```html
<profesor id="p9" sexo="mujer">
   <nombre>María Isabel</nombre>
   <apellidos>Peinado Sanjuán</apellidos>
</profesor>
```

Una o més aparicions, que es expressa amb el signe de la suma:

```html
<!ELEMENT claustro (profesor)+>
```

Per tant, un claustro està constituido per professors, però almenys ha d'haver un.

Cap, una o més aparicions, que es expressa amb l'asterisco:

```html
<!ELEMENT claustro (profesor)*>
```

Amb aquesta definició, el claustro podria estar buit.

## **Sintaxi i estructura de DTD**

DTD (Document Type Definition) és la forma més antiga de definir gramátiques per a XML. La seua importància hui en dia és principalment formativa, ja que permet comprendre els fundamentos teórics dels llenguatges de marques.

La sintaxi de DTD és concisa i simbólica, heredera de les primeres gramátiques formals. El seu objectiu és descriure estructures, no significats. DTD descriu què elements poden aparèixer en un document XML i com es relacionen entre sí, però no entra en el detall semàntic de les dades.

DTD no utilitza XML com sintaxi, sinó un llenguatge propi, el que refuerza el seu caràcter teóric.

### **Elements amb <!ELEMENT>**

Defineix un element i què contingut pot tindre. Permet indicar:

- què fills pot contindre un element.

- l'ordre d'eixos fills.

- si poden repetir-se o omitir-se.

> **📌 <!ELEMENT>**
> 

> Sintaxi General:

```html
<!ELEMENT nombre_del_elemento contenido>
```

On el contingut descriu **què pot contindre eixe element**.

```html
<!ELEMENT pedido (cliente, producto+, total)>
```

Aquesta exemple indica que l'element comanda conté, en aquest ordre, un element client, un o més elements producte i un element total.

La sintaxi entre parèntesis defineix una expressió de contingut, molt similar a una gramàtica formal

Aquest DTD validaría un XML com aquest:

```html
<!DOCTYPE pedido SYSTEM "pedido.dtd">
<pedido>
    <cliente>Juan</cliente>
    <producto>Teclado</producto>
    <producto>Ratón</producto>
    <total>cuarenta y cinco</total>
</pedido>
```

#### **Operadors**

Els operadors permeten definir la cardinalitat i relació entre elements:

- "?" → l'element és opcional (zero o una vegada).

- "*" → l'element pot aparèixer zero o més vegades.

- "+" → l'element ha d'aparèixer una o més vegades.

- "|" → elecció entre diversos elements.

- "," → seqüència, indica ordre obligatori.

Aquests operadors són la base de la gramàtica estructural en DTD.

### **Atributs amb <!ATTLIST>**

Defineix els atributs d'un element, indicant:

- el seu nom.

- el seu tipus (molt bàsic).

- si són obligatoris o opcionals.

> **📌 <!ATTLIST>**
> 

> Sintaxi General:

```html
<!ATTLIST elemento atributo tipo modificador>
```

Exemple:

```html
<!ATTLIST pedido id CDATA #REQUIRED>
```

En aquest exemple es indica que l'element comanda té un atribut anomenat id, de tipus text i que és obligatori.

Els valors que es poden especificar són:

- 

# REQUIRED → obligatori

- 

# IMPLIED → opcional

- "valor" → valor per defecte

- 

# FIXED "valor" → valor fix (no pot canviar)

DTD permet pocs tipus d'atributs i poques regles, el que refuerza el seu enfocament estructural.

### **Limitacions estructurals**

DTD presenta importants limitacions tècniques:

- No permet definir tipus de dades: tot el contingut és text.

- No suporta namespaces, el que dificulta combinar vocabularios.

- No permet validacions complexes ni regles semàntiques.

- Té una sintaxi pròpia, distinta de XML.

Per aquestes raons, DTD és insuficiente per a sistemes moderns, però segueix sent molt útil per a entendre el concepte de gramàtica.

> **📌 DTD**
> 

> 

```html
<!ELEMENT pedido (cliente, producto+, total)>

<!ELEMENT cliente (#PCDATA)>
<!ATTLIST cliente id CDATA #REQUIRED>

<!ELEMENT producto (#PCDATA)>

<!ELEMENT total (#PCDATA)>
```

El XML que es valida

```html
<!DOCTYPE pedido SYSTEM "pedido.dtd">
<pedido>
    <cliente id="12">Juan</cliente>
    <producto>Teclado</producto>
    <producto>Ratón</producto>
    <total>cuarenta y cinco</total>
</pedido>
```

## **Sintaxi i estructura de XSD**

XSD (XML Schema Definition) és l'evolució natural de DTD i l'estàndard oficial del W3C per a definir documents XML.
La versió 1.1 és la més completa i la que segueix vigent actualment.

A diferència de DTD, XSD permet una descripció precisa, tipada i extensible dels documents XML.

### **Tipus simples**

Els tipus simples defineixen valors atòmics, és a dir, dades sense estructura interna.
Exemples habituals:

- xs:string

- xs:integer

- xs:decimal

- xs:boolean

- xs:date

- xs:dateTime

Sobre aquests tipus es poden aplicar restriccions, com:

- valors mínims i màxims (minInclusive, maxInclusive),

- longituds (length, minLength, maxLength),

- patrons mitjançant expressions regulars (pattern).

Açò permet validar no només l'estructura, sinó també el contingut.

### **Tipus complexos**

Els tipus complexos permeten definir estructures formades per diversos elements i atributs.
S'utilitzen per a:

- agrupar dades relacionats,

- definir jerarquías,

- modelar entitats completes.

Dins dels tipus complexos s'usen construccions com:

- xs:sequence → els elements han d'aparèixer en un ordre concret.

- xs:choice → es permet triar entre diverses opcions.

- xs:all → els elements poden aparèixer en qualsevol ordre (amb limitacions).

### **Namespaces**

Els namespaces permeten identificar de forma única els elements d'un vocabulari XML.
Són fonamentals quan:

- es combinen distints esquemes,

- es integren sistemes diferents,

- es reutilizan definicions.

XSD suporta namespaces de forma completa, a diferència de DTD.

### **Herencia de tipus**

XSD permet reutilitzar i extender definicions mitjançant:

- xs:extension → ampliar un tipus existent.

- xs:restriction → limitar un tipus existent.

Aquest mecanisme facilita:

- la reutilització,

- el manteniment,

- l'evolució dels esquemes.

### **Regles avançades**

XSD 1.1 introdueix capacitats addicionals molt potents:

- xs:assert → permet definir regles lògiques usant expressions XPath.

- Validacions que depenen de diversos elements alhora.

- Major flexibilitat per a expressar restriccions semàntiques complexes.

Açò converteix a XSD 1.1 en una eina molt potent per a validacions estructurals avançades en XML.

> **📌 XSD**
> 

> 

```html
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">

<xs:element name="usuario" type="usuarioType"/>

<xs:complexType name="usuarioType">
    <xs:sequence>
        <xs:element name="nombre" type="xs:string"/>
        <xs:element name="edad" type="xs:integer"/>
    </xs:sequence>
</xs:complexType>

</xs:schema>
```

El XML que es valida

```html
<usuario xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:noNamespaceSchemaLocation="usuario.xsd">
<nombre>Ana</nombre>
<edad>25</edad>
</usuario>
```

## **Sintaxi de JSON Schema**

JSON Schema és l'estàndard per a descriure i validar documents JSON.
La versió Draft 2020‑12 és la més extendida i recomanada en entorns professionals actuals, i serveix de base per a l'evolució cap a JSON Schema 2.0.

### **Elements fonamentals**

Els components bàsics d'un schema són:

- $schema: Indica què versió de l'estàndard es està utilitzant. En entorns moderns és obligatori per a evitar ambigüetats.

- $id: Identificador únic del schema, normalment una URL.

- type: Defineix el tipus de dada esperat: string, object, array, number, integer, boolean.

- properties: Defineix les propietats d'un objecte i el seu tipus.

- required: Llista de camps obligatoris.

- additionalProperties: Permet controlar si es accepten propietats no definides.

- $ref: Permet reutilitzar altres schemas, favorecent la modularitat.

### **Novetats introduïdes**

La versió 2.0 amplia les capacitats de l'estàndard amb:

- Validació condicional mitjançant if, then, else, que permet expressar regles dependientes del context.

- Vocabularios modulars, que faciliten extensions controlades de l'estàndard.

- Tipus més expresivos, combinant regles i restriccions.

- Missatges d'error més clars, orientats a millorar l'experiència del desenvolupador.

Aquestes mejoras permeten que JSON Schema es acerque més al model conceptual real del domini, sense sustituir la lògica de negoci.

> **📌 JSON Schema**
> 

> 

```html
{
"$schema": "https://json-schema.org/draft/2020-12/schema",
"$id": "https://example.com/usuario.schema.json",
"type": "object",
"properties": {
    "nombre": { "type": "string" },
    "edad": { "type": "integer" }
},
"required": ["nombre", "edad"]
}
```

El JSON que valida

```html
{
"nombre": "Ana",
"edad": 25
}
```

Ara JSON Schema amb condicionals com if i else

```html
{
"type": "object",
"properties": {
    "tipo": { "enum": ["normal", "admin"] },
    "email": { "type": "string", "format": "email" },
    "permisos": {
    "type": "array",
    "items": { "type": "string" }
    }
},
"required": ["tipo", "email"],
"if": {
    "properties": { "tipo": { "const": "admin" } }
},
"then": {
    "required": ["permisos"]
}
}
```
