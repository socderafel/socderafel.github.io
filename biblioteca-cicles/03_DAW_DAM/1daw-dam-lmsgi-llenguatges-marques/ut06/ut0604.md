# **Creació de descripcions de documents**

Crear una descripció de documents no consisteix simplement en escriure un fitxer DTD, XSD o JSON Schema. En realitat, implica **dissenyar un contrato de dades formal**, que permeta que distints sistemes informàtics intercanvien informació de manera clara, coherent i sense ambigüetats.
Aquest procés és conceptualment molt similar a altres tasques habituals en el desenvolupament de programari, com:

- dissenyar un **model de dades** per a una base de dades.

- definir una **interfície pública** entre components.

- establir un **contrato de comunicació** entre serveis distribuïts.

En tots aquests casos, l'objectiu és el mateix: que totes les parts implicades compartan una **mateixa interpretació de les dades**.
Una descripció de documents bé dissenyada ha de permetre, entre altres coses:

- **validar automàticament** els documents intercambiats.

- **detectar errors l'abans possible**, preferiblement en el punt d'entrada del sistema.

- **garantir la coherència** entre diferents aplicacions, mòduls o serveis.

- facilitar la **evolució del sistema** sense romper compatibilitat.

Quan aquestes descripcions estan malament dissenyades o són incompletas, els problemes apareixen fins i tot encara que la tecnologia utilitzada siga correcta.

## **Principis generals abans de crear una descripció**

Abans d'escriure qualsevol gramàtica o esquema, és imprescindible realitzar un **anàlisi del domini del problema**.
Aquest anàlisi és independent de la tecnologia concreta que es vaja a utilitzar i constituye la base d'una bona definició.
Algunes preguntes clau que han de responderse en aquesta fase són:

- Què tipus d'informació es intercambia entre els sistemes?

- Què entitats principals existeixen en el domini?

- Què camps són obligatoris i quins opcionals?

- Què tipus de dades ha de tindre cada camp?

- Existeixen regles que dependan d'altres camps?

- Aquestes dades es reutilizarán en altres documents o APIs?

- Serà necessari extender aquesta definició en el futuro?

Respondre a aquestes preguntes permet **anticipar problemes** i dissenyar una descripció més robusta.
Una descripció malament planteada genera errors estructurals, incoherencias semàntiques i dificultades de manteniment, fins i tot encara que el validador estiga correctament implementat.

## **Crear un DTD**

DTD és la forma més bàsica de descriure documents XML. El seu objectiu principal no és validar tipus de dades ni expressar regles complexes, sinó **definir l'estructura general del document**.
Per aquest motiu, DTD resulta especialment útil en una fase inicial d'aprenentatge, ja que obliga a pensar en termes de **jerarquia, ordre i cardinalitat**.

Per a poder seguir els passos anem a prendre el següent XML com exemple:

> **📌 XML**
> 

```html
<!DOCTYPE pedido SYSTEM "pedido.dtd">
    <pedido id="P001">
        <cliente>Ana</cliente>
        <producto>Teclado</producto>
        <producto>Ratón</producto>
        <total>45</total>
    </pedido>
```

### **Identificar les entitats del domini**

El primer pas consisteix en identificar els conceptes principals que apareixen en el document.
Cada un d'aquests conceptes sol convertir-se en un element XML.
Per exemple, en un sistema de comandes, és habitual trobar entitats com:

- comanda

- client

- producte

- total

Aquest procés no depèn de DTD, sinó de l'anàlisi del domini del problema.

### **Modelar la jerarquia d'elements**

Una vegada identificades les entitats, cal decidir com es relacionen entre sí:

- quin serà l'element arrel del document.

- què elements contenen a altres.

- en què ordre han d'aparèixer.

DTD obliga a definir de forma explícita aquesta jerarquia, el que ajuda a detectar inconsistencias des del principi.

Exemple: Una comanda conté un client, diversos producte i un total.

> **📌 DTD**
> 

```html
<!ELEMENT pedido (cliente, producto+, total)>
```

### **Definir atributs**

A més del contingut principal dels elements, molts documents necessiten atributs, per exemple per a identificar una comanda o assignar un codi.

En DTD, els atributs s'usen principalment per a:

- identificadors.

- metadades.

- informació auxiliar que no forma part del contingut principal de l'element.

Encara que el seu tipat és molt limitat, permeten enriquecer l'estructura bàsica del document.

Exemple: id d'una comanda.

> **📌 DTD**
> 

```html
<!ATTLIST pedido id CDATA #REQUIRED>
```

### **Especificar cardinalitats**

S'usen els operadors de DTD per a indicar:

- elements obligatoris.

- elements repetits.

- elements opcionals.

Aquest pas és clau, ja que determina què documents seran considerats vàlids des del punt de vista estructural.

DTD utilitza operadors per a indicar cardinalitat:

- "+" → una o més vegades,

- "*" → zero o més vegades,

- "?" → zero o una vegada,

- sense operador → exactament una vegada.

> **📌 DTD**
> 

> 

```html
<!ELEMENT pedido (cliente, producto+, total)>
```

Ací es veu clarament:

- client → obligatori (una vegada),

- producte+ → un o més,

- total → obligatori (una vegada).

### **Limitacions i documentació externa**

DTD no pot expressar regles semàntiques ni validar el contingut de les dades.
Per aquest motiu, és habitual que certes regles deban documentar-se externament, per exemple:

“El camp total representa un importe numèric expresado en euros.”

Aquesta necessitat posa de manifiesto les limitacions de DTD i justifica l'evolució cap a tecnologies més potents.

### **Exemple**

<details markdown="1">

<summary>💡 Exemple Complet</summary>

> **📌 DTD**
> 

```html
<!ELEMENT pedido (cliente, producto+, total)>
<!ATTLIST pedido id CDATA #REQUIRED>

<!ELEMENT cliente (#PCDATA)>
<!ELEMENT producto (#PCDATA)>
<!ELEMENT total (#PCDATA)>
```

> **📌 XML**
> 

```html
<!DOCTYPE pedido SYSTEM "pedido.dtd">
<pedido id="P001">
    <cliente>Ana</cliente>
    <producto>Teclado</producto>
    <producto>Ratón</producto>
    <total>45</total>
</pedido>
```

- 

El DTD valida:

  - l'estructura.

  - l'ordre.

  - l'existència dels elements.

- 

No pot validar:

  - que total siga numèric.

  - que tinga un valor coherent.

</details>

## **Crear un XSD**

XSD (XML Schema Definition) és la tecnologia estàndard definida pel W3C per a descriure documents XML de forma **formal, tipada i extensible**.
Està pensada per al seu ús en **entorns professionals**, on no basta amb comprovar que un document té una estructura correcta, sinó que també és necessari validar que **les dades tenen sentit** i compleixen les regles del domini.

Mentre que DTD es centra exclusivament en l'estructura jeràrquica del document (què elements existeixen, en què ordre apareixen i quantes vegades poden repetir-se), XSD dóna un pas més i permet validar aspectes molt més ricos del contingut, com:

- el **tipus de dada** de cada element o atribut.

- els **rangs de valors** permesos.

- els **formats de text** (dates, identificadors, codis).

- les **relacions entre distints elements** del document.

Gràcies a aquestes capacitats, XSD es converteix en una eina clau per a garantir la **integritat de les dades** intercambiats entre sistemes.

### **Identificar l'element arrel**

A l'igual que en DTD, el primer pas al crear un XSD consisteix en identificar el **element arrel** del document XML.
Aquest element representa la **entitat principal del domini** i actua com punt d'entrada per al procés de validació.
Definir correctament l'element arrel és fonamental, ja que:

- determina què documents poden ser validats amb l'esquema.

- estableix el context general del document.

- organitza el resta d'elements que depenen d'ell.

Per exemple, en un sistema de comandes, l'element arrel sol ser "", mentre que en un sistema d'usuaris seria "" o "". A partir d'aquest element arrel es construeix tota l'estructura del document.

> **📌 XSD**
> 

```html
<xs:element name="pedido"/>
```

### **Crear tipus complexos**

Una de les principals aportacions de XSD enfront de DTD és la possibilitat de definir **tipus complexos**.
Un tipus complex permet agrupar diversos elements relacionats i modelar entitats completes del món real, com un usuari, una comanda o una reserva.
Gràcies als tipus complexos, és possible:

- combinar múltiples elements i atributs.

- definir estructures jeràrquiques internes.

- reutilitzar definicions en distints punts de l'esquema.

Aquest enfocament favorece la **modularitat** i fa que els esquemes siguen més llegibles i mantenibles, especialment en documents grans o en sistemes que evolucionan amb el temps. En lloc de redefinir la mateixa estructura una i una altra vegada, es pot definir un tipus complex una sola vegada i reutilitzar-lo allí on siga necessari.

Els tipus complexos agrupen diversos elements relacionats.

> **📌 XSD**
> 

```html
<xs:complexType name="pedidoType">
    <xs:sequence>
        <xs:element name="cliente" type="xs:string"/>
        <xs:element name="total" type="xs:decimal"/>
    </xs:sequence>
</xs:complexType>
```

### **Aplicar restriccions als tipus**

Una altra avantatge clau de XSD és la possibilitat d'aplicar **restriccions** sobre els tipus de dades.
XSD no només permet indicar que un dada és un número o una cadena de text, sinó que també pot limitar **què valors concrets són vàlids**.

Entre les restriccions més habituals es troben:

- valors mínims i màxims per a números.

- longituds mínimes i màximes per a cadenes.

- patrons mitjançant expressions regulars per a validar formats concrets.

- valors permesos dins d'un conjunt tancat.

Gràcies a aquestes restriccions, errors comuns com números negativos inesperats, cadenes buides o formats incorrectos poden detectar-se **abans de que les dades arriben al codi de l'aplicació**.

Aquest tipus de validació temprana redueix la complexitat del programari i evita errors difícils de depurar en fases posteriors.

XSD permet validar contingut, no només estructura.

> **📌 XSD**
> 

```html
<xs:element name="total">
    <xs:simpleType>
        <xs:restriction base="xs:decimal">
        <xs:minInclusive value="0"/>
        </xs:restriction>
    </xs:simpleType>
</xs:element>
```

### **Definir atributs tipats i regles**

En XSD, els atributs deixen de ser simples valors de text sense significat, com ocorre en DTD, i passen a formar part real del **model de dades**.

Els atributs en XSD:

- estan correctament tipats.

- poden ser obligatoris o opcionals.

- poden tindre restriccions de valors.

- participen activament en la validació del document.

Açò permet dissenyar documents XML més precisos i coherentes, en els que tant els elements com els atributs segueixen regles clares i bé definides.

> **📌 XSD**
> 

```html
<xs:attribute name="id" type="xs:string" use="required"/>
```

Els atributs ara estan tipats i bé definits.

### **Modularitzar schemas**

En projectes reals, els esquemes XSD rara vegada es concentran en un únic arxiu.
El més habitual és dividir la definició en diversos esquemes especialitzats, per exemple:

- esquemes amb tipus comuns reutilitzables.

- esquemes específics per a cada entitat principal.

- esquemes compartits entre distints documents o sistemes.

Aquesta modularizació facilita:

- el manteniment del projecte.

- la reutilització de definicions.

- l'evolució del sistema sense romper compatibilitat.

Gràcies als mecanismes d'importació i referència, XSD permet construir **sistemes d'esquemes complexos però bé organitzats**, alguna cosa imprescindible en entorns empresarials.

### **Regles avançades**

La versió 1.1 de XSD introdueix una millora molt important: la possibilitat de definir **regles lògiques avançades** que relacionen distints valors del document.
Aquestes regles permeten validar la **coherència global** del document, no només elements individuals. Per exemple, és possible expressar condicions com:

- una data d'inici ha de ser anterior a una data de fi.

- un importe total ha de ser major que zero.

- certs camps només són vàlids si altres tenen un valor determinat.

Encara que XSD no sustituye la lògica de negoci completa, aquestes regles permeten trasladar part de la validació al propi esquema, millorant la fiabilitat i reduint la complexitat del codi de l'aplicació.

> **📌 XSD**
> 

```html
<xs:assert test="total &gt; 0"/>
```

Açò permet validar coherència global del document.

### **Exemple**

<details markdown="1">

<summary>💡 Exemple Complet</summary>

Un document XML vàlid hauria de tindre una forma similar a aquesta:

> **📌 XML**
> 

```html
<pedido id="P001">
    <cliente>Ana</cliente>
    <producto>Teclado</producto>
    <producto>Ratón</producto>
    <total>45.50</total>
</pedido>
```

El nostre objectiu és crear un XSD que acepte documents com aquest i rechace els incorrectos.

> **📌 XSD**
> 

```html
<?xml version="1.0" encoding="UTF-8"?>
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema"
        elementFormDefault="qualified"
        version="1.1">

    <!-- Tipo simple reutilizable -->
    <xs:simpleType name="importePositivo">
        <xs:restriction base="xs:decimal">
            <xs:minInclusive value="0"/>
        </xs:restriction>
    </xs:simpleType>

    <!-- Tipo complejo del pedido -->
    <xs:complexType name="pedidoType">
        <xs:sequence>
            <xs:element name="cliente" type="xs:string"/>
            <xs:element name="producto" type="xs:string" minOccurs="1" maxOccurs="unbounded"/>
            <xs:element name="total" type="importePositivo"/>
        </xs:sequence>

        <xs:attribute name="id" type="xs:string" use="required"/>

        <!-- Regla avanzada XSD 1.1 -->
        <xs:assert test="total &gt; 0"/>
    </xs:complexType>

    <!-- Elemento raíz -->
    <xs:element name="pedido" type="pedidoType"/>

</xs:schema>
```

</details>

## **Crear un JSON Schema**

JSON Schema és la tecnologia clau per a **descriure, validar i documentar documents JSON** en sistemes moderns. És especialment important en el desenvolupament de **APIs, backends i arquitectures distribuïdes**, on les dades han d'intercambiar-se de forma clara i sense ambigüetats.

Crear un JSON Schema professional no consisteix únicament en indicar què propietats té un JSON, sinó en definir **un contrato de dades complet**, que describa:

- l'estructura del document.

- els tipus de dades esperats.

- què camps són obligatoris.

- què restriccions han de complir-se.

- què regles depenen del context.

Aquest procés es realitza de forma progresiva, seguint una sèrie de passos que ayudan a construir schemas clars, mantenibles i reutilitzables.

### **Declarar el draft**

El primer pas al crear un JSON Schema és indicar **què versió de l'estàndard es està utilitzant**. Açò es fa mitjançant la propietat $schema.

> **📌 JSON Schema**
> 

```html
"$schema": "https://json-schema.org/draft/2020-12/schema"
```

Aquesta declaració és fonamental perquè evita interpretacions ambiguas del schema.
Els validadors i eines necessiten saber **què regles han d'aplicar**, ja que distintes versions de l'estàndard poden comportar-se de forma diferent.

En entorns professionals actuals, declarar el draft **no és opcional**, sinó una bona pràctica imprescindible per a garantir compatibilitat entre eines.

### **Afegir un identificador**

Un JSON Schema professional ha de tindre un **identificador únic**, definit mitjançant la propietat $id.

> **📌 JSON Schema**
> 

```html
"$id": "https://example.com/schemas/pedido.json"
```

Aquest identificador compleix diverses funcions importants:

- Permet **referenciar el schema des d'altres schemas**.

- Facilita l'organització dels esquemes en projectes grans.

- Permet que APIs i validadors identifiquen de forma inequívoca l'esquema.

En sistemes reals, aquest identificador sol ser una URL, fins i tot encara que el schema no estiga publicat públicament.

### **Especificar el tipus principal**

Una vegada identificada la versió i el schema, cal indicar **què tipus de dada descriu el document**.

> **📌 JSON Schema**
> 

```html
"type": "object"
```

La majoria de documents JSON utilitzats en APIs descriuen **objectes**, és a dir, conjunts de propietats amb claus i valors.

Definir el tipus principal permet detectar errors estructurals molt bàsics, per exemple si es rep un array quan es esperava un objecte o viceversa.

### **Definir les propietats del document**

El següent pas consisteix en descriure **què propietats pot tindre l'objecte** i què tipus té cada una.

> **📌 JSON Schema**
> 

```html
"properties": {
    "cliente": {
        "type": "string"
    },
    "total": {
        "type": "number",
        "minimum": 0
    }
}
```

Ací es està definint que:

- client ha de ser una cadena de text.

- total ha de ser un número i, a més, no pot ser negatiu.

Aquest pas és essencial perquè tradueix el **model conceptual del domini** (comanda, usuari, producte…) a regles formals que el sistema pot validar automàticament.

### **Establir els camps obligatoris**

Definir propietats no implica que totes siguen obligatòries.

Per a indicar què camps han d'existir sempre en el document s'utilitza la propietat required.

> **📌 JSON Schema**
> 

```html
"required": ["cliente", "total"]
```

Aquesta definició evita documents incompletos, per exemple comandes sense client o sense importe total.

Des del punt de vista del desenvolupament, aquesta validació temprana evita tindre que comprovar manualment en codi si les dades existeixen, reduint errors i simplificant la lògica del backend.

### **Afegir validació condicional**

En molts sistemes reals, les regles no són sempre iguals: depenen del context o d'altres camps.
JSON Schema 2.0 permet modelar aquestes situacions mitjançant **validació condicional**.

> **📌 JSON Schema**
> 

```html
"if": {
    "properties": {
        "tipo": {
            "const": "premium"
        }
    }
},
"then": {  "required": ["descuento"]}
```

Aquesta definició expressa una regla del domini de forma clara: Si el tipus de client és “premium”, llavors el camp descompte ha d'existir.

Gràcies a aquesta funcionalitat:

- es evita duplicar schemas.

- es modelan variants del mateix document.

- el schema es acerca més a la realitat del negoci.

Aquest tipus de validació és un dels grans avances de JSON Schema en versions modernes.

### **Separar schemas i usar referències**

En projectes reals, els schemas no solen escriure's en un únic arxiu gran.
El més habitual és **separar les definicions** i reutilizar-les mitjançant referències.

> **📌 JSON Schema**
> 

```html
"$ref": "./cliente.schema.json"
```

Aquest enfocament permet:

- reutilitzar definicions comuns (client, adreça, producte…).

- mantindre els schemas més simples i llegibles.

- facilitar el manteniment i l'evolució del sistema.

La modularizació converteix a JSON Schema en una eina verdaderament escalable, adequada per a projectes medianos i grans.

### **Exemple**

<details markdown="1">

<summary>💡 Exemple Complet</summary>

Per a validar aquest JSON, amb una comanda premium i un altre que no l'és:

> **📌 JSON**
> 

```html
{
    "cliente": "Ana",
    "tipo": "premium",
    "total": 120.50,
    "descuento": 10
}

{
    "cliente": "Luis",
    "tipo": "normal",
    "total": 45
}
```

crearem el JSON Schema per a validar-lo

> **📌 JSON Schema**
> 

```html
{
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "$id": "https://example.com/schemas/pedido.schema.json",

    "type": "object",

    "properties": {
        "cliente": {
            "type": "string",
            "minLength": 1
        },
        "tipo": {
            "type": "string",
            "enum": ["normal", "premium"]
        },
        "total": {
            "type": "number",
            "minimum": 0
        },
        "descuento": {
            "type": "number",
            "minimum": 0
        }
},

"required": ["cliente", "tipo", "total"],

"if": {
    "properties": {
    "tipo": { "const": "premium" }
    }
},
"then": {
    "required": ["descuento"]
},

"additionalProperties": false
}
```

</details>
