En els sistemes informàtics actuals, les dades no es transmeten de forma aïllada, sinó com documents estructurats que han de ser interpretats correctament per diferents aplicacions, serveis i llenguatges de programació.
Un llenguatge de marques (com XML o JSON) proporciona una sintaxi comú per a representar informació, però no defineix per sí només el significat ni les regles del contingut.
Per aquest motiu, és necessari descriure explícitament l'estructura i les regles que han de complir els documents, de forma que tots els sistemes implicats compartan el mateix model de dades.
Aquesta descripció es coneix com contrato de dades i es materializa mitjançant tecnologies com:

- **DTD** i **XSD** en XML

- **JSON Schema** en JSON

- **OpenAPI** per a APIs web

## **Document Bé format vs Document vàlid**

En qualsevol llenguatge de marques (XML, JSON, YAML…), un document pot evaluar-se en dos nivells distints de correcció:

### **Document bé format**

Un document bé format compleix únicament les regles sintàctiques bàsiques del llenguatge en el que està escrit.

Aquestes regles garanteixen que el document pot ser llegit i processat per un parser, però no garanteixen que les dades tinguen sentit.

Exemples:

#### **En XML**

- Totes les etiquetes estan correctament abiertas i cerrades.

- Les etiquetes estan bé imbricades.

- Els atributs van entre cometes.

- Existeix un únic element arrel.

#### **En JSON**

- Ús correcte de claus {} i claudàtors [].

- Comes bé colocades.

- Claus entre cometes.

- Tipus vàlids (string, number, boolean, array, object).

Un document bé format no produeix errors de sintaxi, però pot contindre informació incorrecta o incompleta des del punt de vista del sistema.

### **Document vàlid**

Un document vàlid és un document bé format que, a més, compleix una descripció formal prèviament definida, és a dir, una gramàtica o esquema.
Aquestes gramátiques poden ser:

- DTD o XSD per a XML

<details markdown="1">

<summary>💡 **Exemple XML** bé format vs vàlid</summary>

En aquest cas veiem que el document XML està bé format, no té errors de sintaxi.

> **📌 XML**
> 

```html
<usuario>
    <nombre>Ana</nombre>
    <edad>veinticinco</edad>
</usuario>
```

Per a saber si és vàlid hem de validar-lo contra una definició. Suposem la definició d'aquest XSD

> **📌 XSD**
> 

```html
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
<xs:element name="usuario">
    <xs:complexType>
    <xs:sequence>
        <xs:element name="nombre" type="xs:string"/>
        <xs:element name="edad" type="xs:integer"/>
    </xs:sequence>
    </xs:complexType>
</xs:element>
</xs:schema>
```

Podem observar que el document XML està bé format però no és vàlid, l'element edat haurà de ser integer i en el nostre exemple és string.

</details>

- JSON Schema per a JSON

<details markdown="1">

<summary>💡 **Exemple JSON** bé format vs vàlid</summary>

En aquest cas veiem que el document JSON està bé format, no té errors de sintaxi.

> **📌 JSON**
> 

```html
{
"precio": "100",
"stock": -5
}
```

Per a saber si és vàlid hem de validar-lo contra una definició. Suposem la definició d'aquest JSON Schema

> **📌 JSON Schema**
> 

```html
{
"type": "object",
"properties": {
    "precio": { "type": "number" },
    "stock": { "type": "integer", "minimum": 0 }
},
"required": ["precio", "stock"]
}
```

Podem observar que el document JSON està bé format però no és vàlid, l'element stock no pot ser menor a 0 i en el nostre exemple és -5.

</details>

Un document vàlid garanteix que:

- Els camps esperats existeixen.

- Els tipus de dades són correctes (número, string, data, email, etc.).

- Es respetan restriccions (longituds, rangs, patrons).

- Es compleix la semàntica del model de dades, no només la sintaxi.

Un document pot ser bé format però no vàlid, però mai pot ser vàlid si no és bé format.

## **Per què necessitem descriure i validar documents?**

En els sistemes moderns (APIs, microservicios, aplicacions web), les dades circulan constantement entre components independents, a menudo desarrollats per equips distints o fins i tot per empreses distintes.

Sense un contrato de dades riguroso, apareixen problemes com:

- Inconsistencias entre serveis.

- Fallades silenciosos difícils de detectar.

- Corrupció de dades en bases de dades.

- Rotura d'integracions amb tercers.

- Errors que apareixen lluny de l'origen del problema.

- Bugs complexos i costosos de depurar.

Per aquest motiu, les bones pràctiques actuals recomanen validar les dades l'abans possible i tantes vegades com siga necessari.

## **Aplicació real en el desenvolupament web**

Exemples reals de problemes per falta de validació

- Una API que rep un JSON sense email
    → El sistema falla més avant a l'intentar enviar notificacions.

- Un microservicio que consume missatges sense validar
    → Dades incorrectos es propagan a altres serveis (efecte cascada).

- Una botiga online que rep preus com strings
    → Errors en càlculs, totals incorrectos, facturació errónea.

Per això els llenguatges de marques van units a descriptors semàntics: DTD, XSD, JSON Schema, OpenAPI.
