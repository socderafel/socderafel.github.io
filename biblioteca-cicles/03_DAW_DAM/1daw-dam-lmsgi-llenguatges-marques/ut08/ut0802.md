En l'apartat anterior vam veure que existeixen quatre grans mètodes per a emmagatzemar documents XML. Ara anem a profunditzar en cada un d'ells, a conèixer els seus **avantatges i inconvenients** i a aprendre a **triar la tecnologia més eficient** segons les característiques del problema.

## **1. Emmagatzematge en fitxers plànols**

És l'opció més simple: el document XML es guarda com un arxiu de text en una carpeta del sistema.

**Avantatges:**
- Senzillesa total: no fa falta instal·lar cap programa.
- Portabilitat: es pot copiar, enviar per correu o pujar a un servidor web sense configuració.
- Legibilitat: qualsevol editor de text permet veure el contingut.

**Inconvenients:**
- Les cerques requereixen recórrer l'arxiu complet (lineal).
- No suporta **concurrencia**: dos processos no poden escriure alhora.
- No garanteix **transaccions** (si el procés falla a mitad, l'arxiu queda corrupto).
- No hi ha control d'accés granular ni còpies de seguretat automátiques.
- Difícil d'escalar quan hi ha milers o milions de documents.

💡 **Exemple:** l'arxiu `configuracion.xml` d'una aplicació és un cas legítimo de fitxer plànol. Però el milió de factures de l'empresa **no** ha de guardar-se així.

## **2. Emmagatzematge en SGBD relacionals**

Les bases de dades relacionals (SQL) emmagatzemen la informació en **taules** formades per files i columnes, i permeten relacionar unes taules amb altres mitjançant claus. Un document XML es pot guardar en una base de dades relacional de dos formes distintes:

### A. Document complet com text o tipus XML

El document XML es guarda en una columna de la taula, sense descomponer. Molts SGBD ofereixen un tipus de dada específic (`xml` en SQL Server i PostgreSQL, `XMLType` en Oracle).

```html
CREATE TABLE facturas (
    id       INTEGER PRIMARY KEY,
    fecha    DATE,
    xml_doc  XML
);

INSERT INTO facturas VALUES (1, '2027-03-02', '
    <factura id="f001">
        <cliente>Ana Pérez</cliente>
        <total>125.80</total>
    </factura>
');
```

**Avantatge:** el document es guarda íntegro i es pot validar amb el tipus XML. **Inconvenient:** per a consultar dins del document cal usar extensions específiques (SQL/XML).

### B. Descomposició del document en taules

El contingut del XML es reparte en les taules de la base de dades seguint el model relacional (una taula per a `facturas`, una altra per a `lineas_factura`, etc.).

**Avantatge:** les consultes SQL clásiques funcionen perfectament. **Inconvenient:** es perd l'estructura del document i cal reconstruirla a l'exportar.

## **3. Emmagatzematge en SGBD natius XML**

Una **base de dades nativa XML** emmagatzema el document XML **com una unitat**, respetant la seua estructura jeràrquica, i permet consultar-lo amb **XQuery** i **XPath**. Els principals sistemes són **eXist-db** i **BaseX**.

**Avantatges:**
- Guarda el document íntegro, sense descomponer.
- Consultes potents sobre l'estructura (XQuery/XPath).
- Gestió de col·leccions de documents.
- Validació amb esquemes (DTD, XSD) integrada.

**Inconvenients:**
- Menys maduras i conegudes que les bases relacionals.
- Eines d'administració més limitades.
- No són la millor opció per a dades molt estructurats tipus facturació masiva.

## **4. Emmagatzematge en SGBD NoSQL documentals**

Les bases **documentals** (l'exemple més famoso és **MongoDB**) emmagatzemen documents en format **JSON** dins de col·leccions. Encara que no són bases natives XML, són fonamentals en el panorama actual perquè JSON és el format d'intercanvi dominante en la Web.

```html
{
  "titulo": "Lenguajes de marcas",
  "autor": "María López",
  "precio": 29.95
}
```

**Avantatges:** gran escalabilitat horitzontal, esquema flexible, integració natural amb JavaScript. **Inconvenient:** no validen XML de forma nativa; el XML ha de convertir-se abans a JSON.

## **5. Emmagatzematge en SGBD orientats a objectes**

Les bases de dades orientades a objectes (**DBOO**) suporten un **model d'objectes puro**, és a dir, no estan basades en extensions d'altres models més clásics com el relacional.

**Característiques:**
- Estan influenciades pels llenguatges de programació orientats a objectes.
- Poden verse com un intento d'afegir la funcionalitat d'un SGBD a un llenguatge de programació.
- Són una alternativa per a l'emmagatzematge i gestió de documents XML.

**Components:**
- **Model d'objectes:** proporciona un model d'objectes estàndard en el que es basan els resta components.
- **ODL** (*Llenguatge de Especificació de Objectes*): llenguatge específic per a la definició d'objectes.
- **OQL** (*Llenguatge de consulta de Objectes*): llenguatge específic per a realitzar consultes contra els objectes.
- **OML** (*Llenguatge de Manipulació de Objectes*): estén el llenguatge de programació per a suportar objectes persistentes, consultes OQL, navegació i transaccions, gràcies als *bindings* per a llenguatges com C++ o Java.

**Relació amb XML:** la transformació d'un document XML a objectes és immediata; una vegada transformat, els objectes els gestiona directament el SGBD i es consulten amb OQL. En canvi, els mecanismes del SGBD (indexació, optimització, processament de consultes) no són específics del model XML.

## **Inconvenients generals d'emmagatzemar informació en XML**

Independentment del mètode triat, convé conèixer els problemes típics del XML com format d'emmagatzematge:

1. **Verboso i pesado:** les etiquetes d'obertura i tancament repeteixen informació, el que infla el mida del document.

1. **Cost de processament:** analitzar (parsear) un XML exige més CPU i memòria que llegir formats més simples.

1. **Falta de tipat natural:** els valors es guarden com text i cal convertirlos explícitament.

1. **Consultes complexes:** sobre un fitxer plànol resultan lentas; sobre una base de dades requereixen llenguatges especialitzats (XPath, XQuery, SQL/XML).

1. **Redundància i desnormalizació:** el mateix dada pot aparèixer repetido en molts documents.

💡 **Exemple de pes:** un document que en JSON ocupa 2 KB pot ocupar 5 KB en XML per les etiquetes. Si s'emmagatzemen un milió de documents, eixa diferència es tradueix en gigabytes extra en disc i en temps de transmissió.

## **Com triar la tecnologia eficient (CE6c)**

La regla pràctica per a decidir el mètode d'emmagatzematge es basa en **les característiques del problema**:

| Característica del problema | Tecnologia recomanada |
| --- | --- |
| Volum xicotet, sense consultes complexes | Fitxer plànol |
| Ja existeix una base relacional i el XML és esporádic | SGBD relacional (tipus XML) |
| Dades molt estructurats amb relacions | SGBD relacional (descompost) |
| Documents jeràrquics amb consultes per estructura | SGBD natiu XML (XQuery) |
| Gran volum, esquema flexible, entorn web/JS | NoSQL documental (MongoDB) |

### 💡 Exemple de decisió

- **Biblioteca** amb 50.000 fitxes de llibres → SGBD **natiu XML** o **relacional** segons vulguem consultar per estructura (XQuery) o per camps (SQL).

- **Facturació** d'una empresa amb dades molt regulars i relacions (client, comanda, línia) → SGBD **relacional** descompost.

- **Logs** d'una aplicació web que genera milers de documents per minut → **NoSQL** (MongoDB).

## **Resum**

- Els mètodes d'emmagatzematge són: **fitxers plànols**, **SGBD relacional**, **SGBD natiu XML**, **NoSQL documental** i, en menor mesura, els **SGBD orientats a objectes**.

- El XML com emmagatzematge té **inconvenients** propis: verbositat, cost de processament i consultes complexes.

- L'elecció de la **tecnologia eficient** depèn del volum, l'estructura de les dades i el tipus de consultes que es necesiten.
