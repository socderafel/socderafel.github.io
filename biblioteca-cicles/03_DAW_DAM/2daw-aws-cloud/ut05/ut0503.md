## Grups de Destí (*Target Groups*) a l'ALB

Un **Target Group** és el conjunt lògic de recursos que reben les peticions encaminades per un balancejador de càrrega:
- Tipus de destinacions permeses: **Instàncies EC2** (per ID), **Adreces IP privades**, **Funcions AWS Lambda** o fins i tot un altre Application Load Balancer.
- Un mateix ALB pot tenir múltiples Target Groups associats a diferents regles d'escolta (*Listeners*).

---

## Comprovacions d'Estat de Salut (*Health Checks*)

El balancejador comprova contínuament la salut de cadascun dels servidors registrats al Target Group enviant una petició periòdica HTTP:

```
[ Application Load Balancer ]
       |
       |--- HTTP GET /health.php ---> [ Instància EC2 #1 ]  ---> Respon "200 OK" (HEALTHY)
       |
       |--- HTTP GET /health.php ---> [ Instància EC2 #2 ]  ---> Timeout / 500 Error (UNHEALTHY)
                                                                 (Es deixa d'enviar trànsit!)
```

### Paràmetres de Configuració d'un Health Check:
1. **Health Check Path:** La ruta URL que es consulta (per exemple: `/health` o `/index.html`).
2. **Interval:** Cada quants segons s'envia la petició (ex: cada 30 segons).
3. **Timeout:** Quants segons s'espera la resposta abans de considerar-la fallada (ex: 5 segons).
4. **Healthy Threshold:** Quantes respostes d'èxit consecutives cal rebre per marcar la instància com a sana (ex: 3).
5. **Unhealthy Threshold:** Quantes fallades consecutives cal rebre per marcar la màquina com a defectuosa i treure-la del balanceig (ex: 2).

---

## Encaminament Basat en Ruta i en Host (*Content-Based Routing*)

L'Application Load Balancer permet definir regles avançades basades en la informació de la petició HTTP:

```
Peticions HTTP entrants a l'ALB:
  ├── https://botiga.com/api/*     ---> Target Group 'Backend-Microserveis'
  ├── https://botiga.com/admin/*   ---> Target Group 'Panell-Administracio'
  ├── https://pagaments.botiga.com ---> Target Group 'Pasarela-Bancaria'
  └── Regla per Defecte (*)        ---> Target Group 'Frontend-Web-Principal'
```

Aquest desacoblament permet que equips de desenvolupament diferents actualitzin el backend o el frontend de forma totalment independent sense necessitat de múltiples balancejadors de càrrega!

---

## Sessions Apegaloses (*Sticky Sessions / Target Group Stickiness*)

Per defecte, l'ALB reparteix les peticions de forma independent utilitzant l'algorisme de Round Robin ponderat. Si la teua aplicació web no és completament *stateless* i guarda la sessió de l'usuari a la memòria RAM del servidor local, cal activar les **Sticky Sessions**:
- L'ALB injecta una galeta (*cookie*) HTTP xifrada al navegador de l'usuari.
- Totes les peticions posteriors d'aquest client es desviaran exactament a la mateixa instància EC2 mentre dure la cookie de sessió.
