El **Projecte Interdisciplinar** és la culminació pràctica del primer curs dels cicles formatius de grau superior (DAW / DAM). Connecta directament els mòduls de **Programació (Java)**, **Bases de Dades (SQL / SGBD)**, **Llenguatges de Marques (HTML/CSS/JSON)** i **Entorns de Desenvolupament (UML, Git, Proves i Qualitat)**. En aquesta unitat s'estableix l'arquitectura de programari en capes, els patrons de disseny estàndard (**MVC**, **DAO**), l'especificació formal de requisits (**IEEE 830**) i el flux de treball col·laboratiu en equip mitjançant repositoris compartits a GitHub.

## 16.1 L'Arquitectura de Tres Capes (*Three-Tier Architecture*)

Per a evitar que la interfície gràfica continga consultes SQL o que les regles de negoci estiguen barrejades amb elements visuals, s'aplica una estricta divisió en tres capes:

```
[ Capa de Presentació / UI ]
             │  (Empra DTOs i crida a mètodes de la capa de serveis)
             ▼
[ Capa de Lògica de Negoci / Serveis ]
             │  (Aplica regles de negoci, càlculs i crida a DAOs)
             ▼
[ Capa d'Accés a Dades / DAO ]
             │  (Executa consultes SQL via JDBC / JPA)
             ▼
[ Base de Dades Relacional (MySQL / MariaDB / PostgreSQL) ]
```

1. **Capa de Presentació (*Presentation Layer*):** Responsable exclusiva d'interactuar amb l'usuari (interfície de consola, escriptori JavaFX/Swing o web). No conté cap regla de negoci ni cap consulta SQL.
2. **Capa de Negoci (*Business Logic / Service Layer*):** Conté els serveis que apliquen les regles del sistema (validar descomptes, calcular nòmines, comprovar condicions de reserva). No sap com es mostren les dades ni com s'emmagatzemen a la base de dades.
3. **Capa d'Accés a Dades (*Data Access Layer / Persistence*):** Implementa els mecanismes d'emmagatzematge físic mitjançant interfícies **DAO**.

## 16.2 Patrons de Disseny Fonamentals

### 1. El Patró DAO (*Data Access Object*)
Aïlla completament la lògica de negoci dels detalls concrets del sistema de gestió de bases de dades (SGBD). Defineix una **interfície Java** amb les operacions CRUD estàndard i una classe d'implementació concreta:

```java
// 1. La Interfície pública desacoblada
public interface AlumneDAO {
    void inserir(Alumne a) throws DAOException;
    Alumne buscarPerId(int id) throws DAOException;
    List<Alumne> llistarTots() throws DAOException;
    void actualitzar(Alumne a) throws DAOException;
    void eliminar(int id) throws DAOException;
}

// 2. La Implementació concreta amb JDBC / SQL
public class AlumneDAOImpl implements AlumneDAO {
    @Override
    public Alumne buscarPerId(int id) throws DAOException {
        String sql = "SELECT id, nom, email FROM alumnes WHERE id = ?";
        // Execució amb PreparedStatement i transformació a objecte Alumne
        return new Alumne(id, "Nom", "email@centre.edu");
    }
    // ...
}
```

### 2. El Patró MVC (*Model-View-Controller*)
- **Model:** Representa les dades i la lògica de l'aplicació (les entitats i serveis).
- **Vista (*View*):** Representa la presentació visual de les dades per a l'usuari.
- **Controlador (*Controller*):** Intercepta les accions de l'usuari (clics, enviaments), invoca els serveis corresponents i selecciona quina vista s'ha de mostrar a continuació.

## 16.3 L'Especificació de Requisits segons l'estàndard IEEE 830 (SRS)

Tot projecte de programari ha d'anar acompanyat del seu document d'**Especificació de Requisits de Programari (*Software Requirements Specification - SRS*)**:
1. **Introducció:** Propòsit, abast del producte i definicions.
2. **Descripció General:** Perspectiva del producte, característiques dels usuaris i restriccions generals.
3. **Requisits Específics:**
   - Llista numerada de **Requisits Funcionals (`RF-01`, `RF-02`...)**.
   - Llista de **Requisits No Funcionals (`RNF-01`...)** (rendiment, seguretat, usabilitat).
   - Diagrames de suport: Diagrama de Casos d'Ús i Diagrama de Classes UML.

## 16.4 Dinàmica de Treball Col·laboratiu amb Git i GitHub

En un projecte en equip de 3 a 4 persones, **està totalment prohibit treballar tots directament sobre la branca `main`**:
1. Es crea un repositori comú a l'organització de GitHub del cicle.
2. La branca `main` es protegeix (*Branch Protection Rules*), requerint almenys una revisió de codi (*Code Review*) abans de poder fusionar.
3. Cada membre crea la seua pròpia branca per a cada tasca:
   `git checkout -b feature/gestio-usuaris`
4. En acabar la tasca i verificar les proves unitàries, es puja la branca i s'obre un **Pull Request (PR)** a GitHub.
5. Els companys d'equip revisen el codi, deixen comentaris i aproven la fusió.

## 📝 Quadern d'Activitats Pràctiques i Reptes de Laboratori

### Bloc A: Fonaments, Dimensionament i Anàlisi de Rendiment

#### Exercici 1: Disseny d'Arquitectura en Capes d'una Plataforma de Streaming
Una plataforma multimèdia rep una petició d'un usuari per visualitzar una pel·lícula:
1. Indica quina de les tres capes (Presentació, Lògica de Negoci o Accés a Dades) és responsable de:
   - Comprovar si la subscripció de l'usuari està activa i no té rebuts impagats.
   - Executar la consulta `SELECT * FROM pelicules WHERE id = ?`.
   - Renderitzar el botó "Reproduir" i l'indicador de bateria al dispositiu de l'usuari.
   - Encriptar les dades de trànsit de vídeo.
2. Què passaria si el desenvolupador col·loca la comprovació de la subscripció directament dins de la interfície d'usuari? Quins problemes de manteniment i seguretat es generarien si demà es llança una versió per a Smart TV?

#### Exercici 2: Anàlisi d'un patró Singleton per a connexions a bases de dades
Observa la següent implementació del patró Singleton en Java:

```java
public class ConnexioBD {
    private static ConnexioBD instancia;
    private ConnexioBD() { /* connexió costosa a MySQL */ }

    public static ConnexioBD getInstancia() {
        if (instancia == null) {
            instancia = new ConnexioBD();
        }
        return instancia;
    }
}
```

1. Per què el constructor de la classe és obligatòriament `private`?
2. Què passaria si $1.000$ usuaris concurrents crearen una instància nova de connexió `new ConnexioBD()` en cada petició en lloc d'utilitzar el patró Singleton?
3. Quin problema pot tindre aquesta implementació bàsica en un entorn amb múltiples fils d'execució (*Multi-threading*) simultanis si dos fils entren alhora a `if (instancia == null)`?

#### Exercici 3: Càlcul de sobrecàrrega de transferència amb DTOs
Un servei web consulta un registre d'un client que a la base de dades conté $35\text{ columnes}$ (dades personals, historial de factures, auditories internes, claus xifrades), ocupant $1.850\text{ bytes}$ per client.
- La pantalla de consulta d'usuaris a l'aplicació només necessita mostrar el `nom`, `email` i `ciutat`.
- Es dissenya un objecte lleuger `ClientResumDTO` que només conté aquests 3 camps, ocupant $75\text{ bytes}$.
1. Si un llistat corporatiu mostra $5.000$ clients alhora:
   - Quin volum de dades en Megabytes es transfereix si s'envia l'entitat completa?
   - Quin volum es transfereix utilitzant el patró DTO?
2. Quin és el percentatge de reducció de trànsit de xarxa obtingut?

### Bloc B: Reptes Pràctics de Laboratori i Taller / Comandes

#### Repte 1: Implementació completa del Patró DAO per a un Catàleg de Cicles
- **Objectiu:** Crear una arquitectura desacoblada per a gestionar entitats `CicleFormatiu`.
- **Procediment de taller:**
  1. Crea la classe entitat `CicleFormatiu` (amb `id`, `codi`, `nom`, `hores`).
  2. Defineix la interfície `CicleFormatiuDAO` amb els mètodes `inserir`, `buscarPerCodi` i `llistarTots`.
  3. Crea la classe `CicleFormatiuDAOMemoria` que implemente la interfície emmagatzemant els objectes en un `ArrayList` intern (ideal per a proves).
  4. Crea una classe `ServeiCicles` que utilize el DAO per verificar que no es poden introduir dos cicles amb el mateix codi.

#### Repte 2: Configuració d'un Repositori Col·laboratiu a GitHub amb Protecció de Branques
- **Objectiu:** Configurar el repositori d'equip del projecte aplicant el flux de Pull Requests.
- **Procediment:**
  1. Crea un repositori a GitHub titulat `projecte-interdisciplinar-grup04`.
  2. Afegeix als teus companys com a col·laboradors amb permisos d'escriptura.
  3. Afegeix un fitxer `.gitignore` per a Java i un fitxer `README.md` amb la descripció del projecte.
  4. Crea una branca `feature/dao-productes`, implementa una classe, fes el commit i puja-la a GitHub.
  5. Obre un **Pull Request**, sol·licita la revisió d'un company i realitza la fusió a `main` un cop aprovat.

#### Repte 3: Redacció del Document d'Especificació SRS (IEEE 830)
- **Objectiu:** Redactar la secció de requisits funcionals i no funcionals del projecte interdisciplinar.
- **Lliurable:** Document Markdown amb:
  - 6 Requisits Funcionals detallats (`RF-01` a `RF-06`).
  - 3 Requisits No Funcionals de seguretat, temps de resposta i disponibilitat.
  - El diagrama de classes UML general de l'aplicació.
