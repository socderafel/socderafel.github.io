Una còpia de seguretat que no s'ha provat mai a restaurar **no és una còpia de seguretat; és un acte de fe**. El pla de recuperació davant desastres (**DRP** - *Disaster Recovery Plan*) és el conjunt de procediments documentats i assajats que permeten aixecar de nou tots els portals i serveis web després d'una pèrdua catastròfica del servidor.

---

## 1. Mètriques Clau de Resiliència: RTO i RPO

Tota organització defineix el seu nivell de tolerància a fallades mitjançant dos paràmetres clau:

```
[ ÚLTIM BACKUP REALITZAT ] ◄── RPO ──► [ MOMENT DEL SINISTRE ] ◄── RTO ──► [ SERVEI RESTAURAT ]
```

1. **RPO (*Recovery Point Objective* - Objectiu de Punt de Recuperació):** La quantitat màxima de dades que l'organització es pot permetre perdre en temps. Si fem backups diaris a les 03:00 i el servidor falla a les 17:00, el nostre RPO és de 14 hores de dades perdudes.
2. **RTO (*Recovery Time Objective* - Objectiu de Temps de Recuperació):** El temps màxim acceptable que el servei pot estar caigut des del moment del desastre fins que els usuaris poden tornar a connectar-se.

---

## 2. El Protocol d'Actualització Segura: Entorns de Staging

Per evitar que una actualització de WordPress, Moodle o Nextcloud trenque el lloc en producció davant dels usuaris:
- **Entorn de Producció (*Live*):** El servidor oficial accessible pel públic.
- **Entorn de Preproducció (*Staging*):** Una còpia clonada exacta en una màquina de laboratori o subdomini privat (`test.iesrafael.local`).
- **Regla d'or:** Les actualitzacions majors es proven primer a *Staging*. Si cap connector falla i la base de dades s'actualitza correctament, es programa l'actualització a producció.

---

## 3. Protocol de Restauració d'Emergència Pas a Pas

En cas de destrucció total d'un servidor web, un tècnic SMX executa el següent pla d'acció sobre una nova màquina neta:

### Pas 1: Instal·lació de la Pila Base (LAMP)
```bash
sudo apt update
sudo apt install -y apache2 mariadb-server php libapache2-mod-php php-mysql
```

### Pas 2: Restauració de la Base de Dades
```bash
# Descomprimir i injectar l'exportació SQL a MariaDB
sudo mariadb -u root -e "CREATE DATABASE IF NOT EXISTS wp_iesrafael CHARACTER SET utf8mb4;"
sudo zcat /var/backups/db_all_2026-11-03.sql.gz | sudo mariadb -u root wp_iesrafael
```

### Pas 3: Restauració dels Fitxers i Permisos
```bash
# Extreure l'arxiu d'aplicacions web
sudo tar -xvzf /var/backups/var_www_2026-11-03.tar.gz -C /

# Assegurar la propietat i permisos estrictes
sudo chown -R www-data:www-data /var/www/
sudo find /var/www/ -type d -exec chmod 755 {} \;
sudo find /var/www/ -type f -exec chmod 644 {} \;
```

### Pas 4: Habilitació del Virtual Host i Comprovació
```bash
sudo a2ensite portal.conf
sudo a2enmod rewrite ssl headers
sudo systemctl restart apache2
```

---

## 4. Simulacres Periòdics de Restauració

Un bon tècnic realitza almenys un simulacre de restauració cada trimestre en una màquina virtual aïllada:
- Mesura el temps real emprat (per verificar si compleix l'RTO).
- Comprova la integritat de la base de dades (comptes d'usuaris, últimes tasques lliurades).
- Documenta qualsevol desviació al llibre de procediments de manteniment del centre.
