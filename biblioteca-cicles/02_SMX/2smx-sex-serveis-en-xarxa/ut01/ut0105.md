En xarxes d'àrea local complexes, l'administrador s'enfronta a dos reptes crítics: com atendre clients ubicats en diferents VLANs sense col·locar un servidor físic a cada subxarxa (**DHCP Relay Agent**) i com garantir que la xarxa continue operativa si el servidor DHCP principal s'avaria (**DHCP Failover**).

---

## 1. El Problema dels Dominis de Difusió i el DHCP Relay Agent

Els paquets inicials de DHCP (`DHCPDISCOVER`) són missatges de **difusió (*Broadcast*)**:
- Per definició, **els encaminadors (routers) i switches de nivell 3 BLOQUEGEN les difusions** per evitar tempestes de broadcast a la xarxa.
- Per tant, si tenim la *VLAN 10 (Alumnat)* i el servidor DHCP està a la *VLAN 100 (Servidors)*, el paquet del client mai arribarà al servidor de manera natural!

### La Solució: L'Agent de Retransmissió DHCP (*DHCP Relay*)
Es configura al router o switch de cada VLAN una funció anomenada **DHCP Relay** (o directiva `ip helper-address` a Cisco):
1. El router rep el paquet `DHCPDISCOVER` per difusió a la interfície de la VLAN 10.
2. El transforma en un paquet **Unicast estàndard** i l'envia directament a la IP del servidor DHCP central a la VLAN 100, afegint el camp `giaddr` (*Gateway IP Address*) indicant d'on prové.
3. El servidor llegeix la petició, sap que pertany a la subxarxa 10 i li retorna l'oferta al router, qui la transmet de nou al client.

```
[ CLIENT VLAN 10 ] ── Broadcast ──> [ ROUTER (DHCP Relay) ] ── Unicast (giaddr 192.168.10.1) ──> [ SERVIDOR DHCP ]
```

---

## 2. Alta Disponibilitat: DHCP Failover

Si el servidor DHCP d'una empresa cau i expiren les concessions, centenars de treballadors es quedaran sense IP ni accés a la xarxa. Amb **DHCP Failover**, dos servidors comparteixen el control del mateix rang:

| Model de Failover | Descripció Operativa | Avantatge Principal |
| :--- | :--- | :--- |
| **Balanç de Càrrega (*Load Balancing*)** | Els dos servidors estan actius simultàniament (ex: 50% de peticions cadascun). | Repartiment eficient de càrrega i redundància instantània |
| **Reserva Calenta (*Hot Standby*)** | El servidor Principal atén el 100% del trànsit. Si cau, el Secundari pren el control immediatament. | Ideal per a servidors centrals amb suport remot |

A Windows Server 2022 o a Linux (ISC-DHCP Failover Protocol), ambdós servidors s'intercanvien constantment missatges de sincronització (*Heartbeat* pel port TCP 647 o 520) per mantindre la taula de concessions replicada en temps real.

---

## 3. Comandes de Diagnosi i Resolució d'Incidències

### En Clients Linux:
```bash
# Alliberar la concessió actual immediatament
sudo dhclient -v -r

# Sol·licitar una nova concessió mostrant el detall per pantalla
sudo dhclient -v

# Consultar l'estat dels fitxers temporals de concessió
cat /var/lib/dhcp/dhclient.leases
```

### En Clients Windows:
```cmd
:: Alliberar la IP actual
ipconfig /release

:: Demanar una nova IP al servidor DHCP
ipconfig /renew

:: Buidar la memòria cau DNS local
ipconfig /flushdns

:: Mostrar tots els paràmetres detallats (servidor DHCP que va atorgar la IP)
ipconfig /all
```
